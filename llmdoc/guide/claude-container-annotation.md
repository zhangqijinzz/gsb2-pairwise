# Claude 容器标注操作指南

入口：选择项目后打开左侧“容器标注”。当前同时保留旧版逐轮五维模式和 Pair-wise GSB 模式，两者使用独立证据结构与导出文件，不能把已有旧版证据直接转换成 Pair-wise。做题详情页的“容器与轨迹”可操作当前题目；已关联项目的题目，其“AI复审”使用同一五维评价缓存。旧版审核历史不会自动转换为五维结果。

## Pair-wise GSB 模式

Pair-wise 用于比较两个模型对同一道题、同一初始代码的首轮结果。当前规则下，AI 负责读取 A/B 轨迹和代码产物、执行必要核验并生成 GSB 结论与理由；要求理由具体、自然并能同时说明 A 与 B 的差异，不能使用空泛模板。人工操作仅在自动录屏不可用时补录并提交两侧功能操作视频。`代码理解`题暂不支持 Pair-wise。

1. 先按旧流程准备题目和 GitHub 初始快照，再点击“启用 Pair-wise GSB”。语言/框架由应用读取仓库自动识别；Harness、Harness 版本和操作系统使用固定运行配置并存入制表数据；环境可复现等级默认留空，有效性默认“有效”。任务难度只能是困难或地狱。题目已有旧版轮次、采集或 Session 时不能直接切换。
2. 点击 A、B 面板各自的“复制启动命令”，使用相同镜像、API Key 和模型配置启动两个不同容器。每侧“绑定”左侧的“刷新容器”会按题号和 A/B 后缀精确匹配；唯一匹配且正在运行时自动绑定。绑定过程会从初始 SHA 自动创建并切换到对应的大写 `A`、`B` 分支，成功后才复制同一提示词。已绑定和已复制按钮显示绿色勾选，但仍可再次操作。A、B 不能绑定同一容器。
3. A、B 必须使用同一个仓库和同一个初始完整 SHA，分支名不能自定义。提交时若仓库仍位于初始 SHA，但处于 detached HEAD 或其他分支，应用会保留未提交代码并自动切换到对应分支；HEAD 或目标分支已经偏离初始 SHA 时不会自动重置。
4. 在两个容器内执行完全相同的 User Prompt。每侧只接受一个完整 Session 的一轮有效交互，A/B SessionID 必须不同。完成后点击“采集 A”“采集 B”，或直接点“一键采集 A/B”按 A、B 顺序各采集一次；应用会扫描该侧绑定容器，按完整 Prompt、仓库路径和完成状态自动匹配唯一主会话，提取 SessionID、冻结轨迹与代码证据，然后自动提交并推送到对应的大写 `A` 或 `B` 分支。某一侧失败时另一侧仍会继续，界面会列出失败侧和已完成侧。没有匹配或存在多条匹配时会停止并提示核对，不会猜选最新文件；单个轨迹文件不能超过 27 MB。
5. 自动提交成功后，界面显示产物 commit 和绿色“已提交 A/B”。产物提交的直接父提交必须是初始 SHA，对应 commit 的完整 GitHub 链接就是该侧产物快照；初始 SHA 不会被产物 commit 替换。若采集已成功但提交或推送失败，冻结证据会保留，可用“提交 A/B 产物”按钮重试。远端最终只应有主分支及大写 `A`、`B` 三个分支。
6. 录屏前点击该侧“复制启动命令”。命令只会运行已提交的最终产物，并强制核对容器、固定大写 `A`/`B` 分支、当前 HEAD 与该侧产物 commit、干净工作区；任一项不符都会停止。把命令粘贴到终端后，它会先打印项目地址，并在容器内项目开始应答后自动打开一次浏览器（最多等 60 秒），也可点击界面上的“打开项目”。命令会把主机代理端口写进本机状态文件，应用据此定位运行中的项目并支持自动录屏；`Command + C` 停止命令时该状态会被自动清理。按 `Command + Shift + 5` 录制实际功能操作，结束录制后把生成的 mp4、mov、webm 或 m4v 文件绝对路径填入该侧并保存，单个文件不超过 500 MB；粘贴时自带的引号会被自动去掉，文件名本身含单引号不受影响。HTTP(S) 链接仅作为兼容输入保留。
7. A/B 轨迹和产物 commit 齐全后可生成 GSB，不必等待视频。理由至少 60 个汉字，分别覆盖 A、B 的执行过程和最终产物；可以使用 AI 分析和生成，但提交文本必须自然、具体、可核验，不得带 AI 式前言、模板化分点或虚构体验。视频未齐时结论显示为临时状态；任一侧证据、产物或视频变化都会使旧结论失效，需要重新生成。
8. 点击“Pair-wise 预检”检查当前题目。预检会读取 GitHub 远端大写 `A`、`B` 分支，核对它们分别指向登记的产物 SHA，且两个产物提交都直接以初始 SHA 为父提交；分支缺失、大小写错误或被移动时，正式导出会阻止。草稿仍可导出并在报告中保留问题。
9. 项目页“批量生成 GSB”会逐题对比冻结的 A/B 轨迹和代码产物，并汇总新审核、复用、跳过和失败数量；证据与模型未变化时直接复用。单题页面仍可独立“生成 GSB”或“重新生成 GSB”。项目页完成 Pair-wise 预检后，可统一导出全部 Pair-wise 题目的草稿或正式表。

Pair-wise 每对结果在 `pairwise-gsb.xlsx` 中占一行，列顺序严格对齐提交页：User Prompt、任务类型、任务难度、语言/框架、Harness、Harness 版本、操作系统、环境可复现等级、初始环境快照、A-SessionID、A-轨迹文件、A-产物快照、A-运行录屏、B-SessionID、B-轨迹文件、B-产物快照、B-运行录屏、GSB 结论、GSB 理由、有效性、备注。只有环境可复现等级和备注可空。导出目录同时包含 `pairwise-report.md`；草稿不会为缺失字段编造内容。

## 准备与执行

“导入并生成文档”的项目选择弹窗可设置每个项目的出题数量：0-1代码生成、Feature迭代、Bug修复可输入非负整数，默认分别为 10、10、2，填 0 则不生成该类型。难度下限为困难，只允许困难与地狱两种标签，默认 20 条困难、2 条地狱，数量可按实际需要调整，但合计必须等于题型总数；简单和一般不再接收。代码理解、工程化、代码测试、代码重构固定为 0 且不生成。生成结果会按题型和难度逐项核对，单条需求低于 60 个有效字符会按简单需求拒绝，数量或难度不符会报错；0-1 代码生成必须是和现有系统深度衔接的完整模块，不再生成空白项目脚手架；Bug修复题需有真实代码依据，不能为凑数量编造。

1. 沿用“自定义提示词文档导入”创建题目。每题源码目录会自动执行独立 Git 初始化提交，保存完整初始 SHA 和初始代码副本。已有但尚未执行的题目可以点“准备题目”。复制源码不携带本机 `node_modules`，依赖应在执行环境安装。文档导入创建题目后，使用设置中的默认 GitHub 账号自动发布冻结的初始提交到独立仓库并回填 commit 链接；发布失败保留题目及本地快照，在详情页点击“发布 GitHub 初始快照”重试。只有一个账号时可自动选用，多账号未设默认时提示配置。
2. 在题目详情“容器与轨迹”点击“复制容器启动命令”，粘贴到本地终端运行。名称取大题名（如 `cyc-03` → `cyc03`），编号取创建时的固定编号，跨题型连续且不随列表排序变化：`cyc03-claude-4`、`$HOME/cyc03-claude-runs/run-4/workspace`。命令不携带密钥；优先使用终端已有 `apikey` 环境变量，否则输入时不回显。固定目录已存在时停止，不覆盖、不自动清理旧题。此镜像在启动检查时要求 `/workspace` 为空，因此先启动新容器，停留在 Claude 等待输入的界面，再导入题目。不要退出后重启同一容器来续轮。
3. 选择容器与 `/workspace` 下的仓库相对路径，点“复制并绑定”。应用复制已提交的源码和 Git 历史，核对初始 SHA；已存在的目录不会覆盖。绑定记录使用真实容器 ID 和 Docker 返回的挂载路径。
4. 在 Claude 输入本题原始 Prompt，可以补充仓库位置。应用将首轮输入与导入的 Prompt、轨迹 cwd 交叉核对；选择其他题目的轨迹会被拦截。
5. 已经执行过的容器使用“关联已有仓库”。已登记初始 SHA 时，执行仓库必须包含该提交。没有真实首轮前快照的旧题保持待补，不能把当前代码补记成初始状态。

应用只自动发布初始快照；不会自动发送被测 Prompt、启动/停止容器、推送后续轮次代码或提交标注。首次绑定若尚无轨迹目录，只用只读目录检查确认它不存在。

新建初始快照仓库按“大题名称-固定编号”命名，例如 `cyc-05-1`，链接为 `https://github.com/<账号>/cyc-05-1/commit/<初始SHA>`。编号与容器命令使用相同的题目 ID/目录依据，不随排序变化；大题名转小写，空格与下划线转为连字符。编号缺失或冲突时提示核对，不回退到哈希名称。已有快照链接不自动重命名，同名仓库发布仍使用非强制推送。

初始快照首次发布到空仓库的 `main`。题目重新创建后，若同名远端已有不同提交，则将本次冻结 SHA 发布到 `initial/<完整SHA>` 分支，保留远端 `main` 和旧快照；链接仍是该仓库的 `/commit/<SHA>`。重复发布同一个 SHA 可直接恢复链接；SHA 对应分支若已被改到其他提交则报错。创建分支使用“远端必须不存在”的空 lease 做并发保护，不覆盖任何已有分支，也不通过 pull、合并或重建提交改变初始 SHA。

## 每轮采集与审核

1. 等 Claude 完成本轮、代码不再变化后，刷新并选择正确的主会话 JSONL，点“采集并准备制表数据”。候选列表不替你猜选会话；也可以输入本机 JSONL 的绝对路径。本机轨迹仍需符合已绑定容器或本地题目仓库的来源关系。
2. 应用保留主轨迹、子代理附件与代码副本，核对采集前后哈希。工具结果、系统事件和压缩摘要不算新轮；无法确定的重复、未结束输入或纯附件输入保留为待处理记录。
3. 采集后自动逐轮审核；需要重评时在“AI复审”点“重新审核”。本机须有已经配置可用的 `codex` CLI；评审执行优先使用 `~/.codex/skills/coding-agent-satisfaction`，不存在时使用应用内置版本；所选技能会冻结到审核目录，并在 input.json 记录来源与哈希。审核，在独立副本中复验。安装目录中的用户 skill 不会在应用启动时被覆盖。
4. 查看交付完整性、指令遵循、任务规划、推理能力、执行能力五项分数和依据。证据不足的项保持空值。重新审核追加一个评价版本，历史结果仍可查看。
5. 五项均为 5 分时显示“五维满分 · 数据已保存”，不生成下轮提示词；功能完成仍可能有过程扣分，非全满分不等于功能不达标；仅有过程问题时保留低分与依据，不生成修复提示词。不再要求填写不满意原因。缺评分时显示待补证据，不编造缺陷；确认的功能遗漏、回归和未解决 Bug 必须记录为 bug，交付完整性低于 5，修复提示词以“修复”开头并写明问题及预期结果。逐项需求核验清单保存在 requirementChecks，显示原需求、已完成/存在未解决问题/尚未核实及具体证据；旧记录不伪造清单，重新审核后补充。审核保存及导出都会阻止满分与 Bug、缺少修复提示词等矛盾；10 个有效轮次后不引导追加轮次，但保留 Bug 修复建议供检查。

每轮结束后及时采集，才能保留准确轮末代码。一次性导入已经跑完的多轮日志时，当前代码仅证明最后一次采集状态；历史轮必须有可重建依据，否则相应维度待补，不能用后续修复后的代码替早期轮评分。

缓存同时核对轨迹、代码及附件版本、规则版本和审核模型配置标识。原始证据或审核验证日志被改动时，不会直接复用旧评分。长任务沿用后台队列，可以取消；取消后的未验证结果不会写成正式评价。

评分描述在同一次 AI 评价中按 `description-quality.md` 逐格复核：非满分须明确本维度的不足、具体行为与证据支持的后果，避免只罗列动作、主观感受词或未定位的风险。未做某种测试不自动等于功能出错或应该扣分；满分依据也要解释所提失误的归属。此检查不新增一轮模型调用、不在数据准备时生成 Excel。规则更新不会改写历史评价，返修旧记录需重新审核并保存新版本；单纯重新导出不会修正文案。

## 已制表内容快捷导出

Excel 的任务类型以导出时题卡上保存的类型为准，同一题各轮保持该类型，AI 自动分类和历史评分缓存不能覆盖；例如题卡为 `0-1代码生成`，Excel 也写 `0-1代码生成`。已有制表数据无需重新审核即可在重新导出时应用这条规则；已生成的旧 Excel 文件不会自动改写。

“采集并准备制表数据”只分析并缓存评分、依据等结构化内容，不生成 Excel 文件；单题或统一导出时才将缓存数据填入模板生成 Excel，不会重新调用 AI 评分。

- 题目详情 → 容器与轨迹：仅保留“采集并准备制表数据”，它在同一后台任务中采集材料并调用 coding-agent-satisfaction，逐轮保存五维评分与依据。无需继续下一轮，修复提示词仅供选择；重试会复用通过校验的缓存。失败或取消保留已采集材料和已完成评分。
- 容器标注页顶部“一键导出已制表”仅汇总当前项目最新评价为 ready 且规则、模型配置和证据匹配的轮次。低分仍可导出；未审核、过期和待补证据轮次不计为已制表，不混入快捷导出。整批草稿导出仍可保留待补记录及缺项报告。
- 题目详情顶部同时提供“导出全项目已制表”，汇总范围是该题所属项目，和容器标注页的批量按钮一致。
- 容器标注页和题目详情顶部的“选择题目导出”可勾选当前项目已有制表数据的题，支持全选与清空，列表可滚动。显示已制表轮次/总轮次，部分制表的题仅导出已保存轮次；点击“导出所选题目”合并成一个 Excel，沿用统一目录和题间空行。空选、跨项目、已删除或无可用制表数据的选择会被阻止，切换项目清空选择。
- 每张题目进度卡、题目详情顶部“导出本题 Excel”只导出该题已制表的轮次。
- 合并 Excel 中，同题多轮连续排列，不同题目之间空一行；空行不计入导出条数。
- 设置 → 通用设置 → Excel 统一导出位置：填写本机绝对目录，所有项目、单题和完整批次导出共同使用该目录。留空使用 `~/.pinru/annotation/exports`。每次创建唯一子目录，包含 `submission.xlsx` 和证据附件，不覆盖以前导出。
- 快捷导出不要求题目完成，也不要求满分；保留材料缺项报告，不能据此宣称正式验收通过。完整批次仍可使用下方预检流程。

## 整批导出

1. 每题填写指向初始提交的 GitHub 完整 commit 链接，链接末尾须为登记的 40 位 SHA。新题自动回填；已有题目可发布此前冻结的初始副本。后续轮次不要求 Git 提交，审核使用采集的代码副本。
2. 确认题目已结束，登记“完成本题”。低分可以结束，不要求五项满分。
3. 填写提交人和真实提交时间，执行“批次预检”。检查覆盖当前项目全部题目和真实轮次，不按旧流程 consumeQuota 或是否满分过滤。
4. 导出只汇总已有评价，不自动启动或恢复已取消的审核。先完成各轮五维审核，再执行导出。材料完整后点“导出本批”。缺少评分、依据、快照、原始轨迹、验证材料，或存在冲突轮次时，正式导出会拦截；仍可导出待补材料，已知分数和依据会保留。

导出目录包含 `submission.xlsx`、`report.md`、`manifest.json`、`evidence.md` 和 `attachments/`。附件包含原始轨迹、代码及审核时独立验证的日志/副本。每次导出使用独立目录并冻结输入清单。应将整个目录作为材料包保存，单独的 Excel 不包含全部证据。

快照与 Pair-wise 分支可访问性通过 GitHub API 验证；优先使用设置中的默认 GitHub 账号令牌，没有令牌时仅能验证公开仓库。私有仓库、网络失败或限流无法确认时会显示待补，仍能保存草稿。

## 数据位置与边界

- SQLite：`~/.pinru/pinru.db`，自动追加 migration 027 保存容器标注记录。
- 证据、审核副本和导出：`~/.pinru/annotation/`。搬迁时应连同数据库保存；仅复制数据库不会携带附件。
- 审核默认使用本机 Codex CLI 配置；`annotation_review_model` 配置键可以显式指定模型。验证环境缺少依赖或工具时，应补环境或保留缺项，不能据此编造测试通过。
- 应用内置 skill 与本次同步后的本机 skill 保留 AI 评价来源。“自然语言”仅整理表达，不修改原始 Prompt、分数、GSB 结论或问题严重性。Pair-wise 的 AI 分析与理由生成属于正式流程，不要求人工代写；人工兜底仅限录屏材料。
- 自动检查主要覆盖字段、完整性和证据一致性；评分语义及项目方接收仍需按实际规范核对，程序通过不代表外部验收通过。

## 状态、续审与出题难度

题卡状态来自数据库中的后台任务与最新评价，刷新和重新打开后仍可恢复显示。排队中、采集中、制表中、制表失败、已取消、待补证据、待重新复审、部分完成、已制表分别展示。“轨迹完整”只说明会话轮次完整，不表示功能完成。

“已复审 x/y 轮”按真实有效轮次计数，同轮重复审核不累计；另列可导出轮数。新增轮次会增加分母，待补证据和过期评价不会显示绿色完成标记。详情显示当前处理轮次、进度、耗时和最后活动时间；两分钟没有新活动只提示等待，不能据此判断断线。已确认进程退出或超过任务时限时显示失败，已保存的数据保留。

“继续准备未完成轮次”读取冻结的本机证据，复用有效评分，不重新采集，也不要求容器仍在运行。采集后的新增对话仍需再次点击“采集并准备制表数据”。

审核规则、轮次证据或审核模型变化会使旧评价标记为待复审。使用 CLI 默认模型时，以 `CODEX_HOME/config.toml`（未设置则为 `~/.codex/config.toml`）的文件指纹判断配置变化；当前采用保守策略，配置中的其他字段变化也会使缓存失效。

导入并生成提示词时，题目难度下限为困难，只生成困难或地狱；导入的文档出现简单或一般会按难度不足拒绝。这是需求复杂度的硬性要求，不是保证产生 Bug 或多轮会话；难度按实际工作量判断。代码理解、工程化、代码测试、代码重构生成时各一条、导入时各最多一条，其余题型数量沿用用户输入。出题须核对现有代码，避免重复已经具备的能力，不为凑 Bug 数量或轮数编造缺陷。
