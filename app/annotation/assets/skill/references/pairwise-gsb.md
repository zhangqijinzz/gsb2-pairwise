# Pair-wise GSB 规则（09/16）

## 适用范围

一道题使用相同环境、相同完整 User Prompt 和相同模型配置独立运行两次，分别记为 A、B。每个 Session 只能有一轮有效交互，两次运行组成一条数据。旧版多轮五维评分不适用于本模式。

来源文档：`【初稿】CC用户反馈标注说明新规范.docx`，SHA-256 `08ff56fee0cccd1389ae71a8a675b2ed7fdbea205246a02482492c3c08e4e1ba`。平台提交页于 2026-09-17 实际核对。

## 提交字段

按以下顺序生成数据：

1. User Prompt
2. 任务类型
3. 任务难度
4. 语言/框架
5. Harness
6. Harness 版本
7. 操作系统
8. 环境可复现等级
9. 初始环境快照
10. A-SessionID
11. A-轨迹文件
12. A-产物快照
13. A-运行录屏
14. B-SessionID
15. B-轨迹文件
16. B-产物快照
17. B-运行录屏
18. A-交付完整性
19. A-交付完整性描述
20. B-交付完整性
21. B-交付完整性描述
22. GSB 结论
23. GSB 理由
24. 有效性
25. 备注（选填）

除 A/B 运行录屏和备注外，其余字段均为必填。环境可复现等级只能为已容器化，可一键起环境、无外部依赖、有外部依赖，未容器化；未单独选择时默认填写已容器化，可一键起环境。任务难度只能为困难或地狱。Harness 使用实际值，只能为 Claude Code 或 Codex CLI。有效性只能为有效、作废-工程故障、作废-环境未重置、作废-其他。

## 运行与快照

- A、B 使用两个不同容器和两个不同 SessionID。
- 镜像、API Key、模型配置、max context token、Harness、Harness 版本、机器、操作系统和 User Prompt 保持一致。
- 全程使用 auto 模型，max context token 固定为 1000000。
- 两次运行共用一个初始环境快照。
- 远端仓库只有主分支 main 或 master，以及大写 A、B，共三个分支。预检必须读取远端实际引用，确认 `refs/heads/A`、`refs/heads/B` 存在且分别指向登记的 A、B 产物 SHA；小写或其他别名不算通过。
- A、B 产物各自使用完整 40 位 SHA 的 commit permalink，且产物提交的直接父提交必须是初始环境快照。
- A、B 轨迹各提交一个不超过 27 MB 的 JSONL 文件。
- A、B 录屏可在 GSB 审核后由人工补充；缺少录屏不阻止审核和导出。补充时每侧提交一个 mp4、mov、webm 或 m4v 文件，不超过 500 MB。

## GSB 审核

结论只能为 A_better、same、B_better，对外分别写为 A 更好、Same、B 更好。A、B 交付完整性分别填写 1—5 的整数和独立描述，沿用五维评分中交付完整性的判断口径：5 为原始需求和关键验收结果均已交付，4 为主体交付且只有非关键缺口，3 为存在影响部分使用的功能遗漏，2 为主要流程未完成，1 为几乎没有可用交付。完整性只评价该侧是否完成原始 User Prompt 要求、交付结果是否可用以及是否存在功能遗漏；描述可以引用该侧证据但不能照抄 GSB 理由，不能把另一侧表现或比较结论写进来。

完整性描述必须与分数一致。5 分只写已经交付的正向依据，不写尚未解决的功能缺口、遗漏、未验证、未执行、证据不足或其他未完成事实；可以说明失败、异常、无法读取、未完成拖拽、缺少草稿或尺寸不足等场景已经如何被成功处理，但必须在同一句或紧邻分句写出清理、恢复、回退、保留、补齐或可用结果，不能把异常条件本身当作缺陷。例如未完成拖拽的收尾清理、尺寸不足时清空草稿属于已交付的处理结果；仍未清理、无法恢复、缺少功能且没有后续处理则仍是缺口。“没有发现问题”这类明确表示未发现缺陷的正向句可以保留。4 分只写一个次要缺口，3 分写 2—3 个缺口，2 分及以下按主要流程未完成的强度递增。验证范围、没有执行某类检查和其他证据边界写在证据或限制说明中，不得混入 5 分完整性描述。若描述中的缺口数量与分数不一致，先重新判断分数，不要靠删句凑数。

理由至少 60 个汉字、最多 320 个字符，并满足：

- 写成一段可以直接放进表单的自然中文，不分点，不套固定标签；
- 先说真正影响结果的差异，再把 A、B 的执行过程和最终产物连起来，不能只写胜方；
- 最后说明这道题最看重什么，以及为什么该判准支持当前结论；
- 过程与产物分别核对，A、B 每侧都至少保留一处过程锚点和一处产物行为。过程锚点至少包含读取、修改或新增的具体文件，执行的命令或验证脚本，真实失败及修正中的一项；只写“运行两侧构建产物”不算过程证据。产物行为要落到用户可观察的功能、交互或可靠性结果；
- 过程问题说清实际行为和业务影响，产物问题说清用户可感知的功能、交互或可靠性差异；
- 评价某侧未修改、未执行、只读未改或停在规划阶段时，必须自然交代触发节点，说明卡在具体文件、函数、命令或业务步骤，不能只写“全程没动文件”；
- Same 要说明采用的判准，以及为什么两边差异不足以改变用户实际结果，不能只用“优缺点抵消”收口；可以直接写出用户结果、行为或效果一致，或两边共同达成的可观察结果，但仍需同时保留 A、B 各自的过程锚点；
- 不考虑推理时长、网络波动和部署导致的无故截断。

篇幅接近上限时，优先保留决定胜负的行为、用户影响和取舍，删去重复背景与次要验证细节。超过 320 个字符时根据原证据完整重写，不能机械截断句子。

证据先完整核验，再为表单压缩。文件、函数、命令、测试或报错只有在能解释关键差异时才写进理由；退出码、行号、版本号、哈希、断言数量、像素坐标和完整日志通常只留在内部证据中。不能用精确数字的堆叠代替对形状差异、验证效果、用户影响和风险的直观说明，也不能为了显得具体而罗列所有检查项。

写表单前先做四格自检：A过程、A产物、B过程、B产物。每格都要能回指一条轨迹或代码证据；两边相同的内容可以合并成“两边都”，但仍须写出对应文件、命令或具体行为。只有构建通过、页面能运行或“实际运行后发现”而没有修改对象、验证动作或用户结果时，按过程证据缺失处理，不得判为过程与产物同时覆盖。

用户已明确允许 AI 分析轨迹、产物并生成 GSB。输出理由不得出现“作为 AI”“根据上述分析”“综合评估”等 AI 式前言，不使用 Markdown、编号、项目符号、反引号、箭头、Emoji、固定标签、模板化分点、机械总结或虚构的亲身体验。禁止使用任何装饰性引号与括号，包括『』、「」、【】、《》〔〕〖〗〘〙〚〛〈〉等，需要引用名称时直接写普通文本；生成结果会直接剔除这类符号，导出前发现残留会按不合格拦截。内部保留 AI 评价来源、完整定位信息和证据哈希，提交字段只保存自然、具体、可核验的理由。写完后按正常中文段落通读一遍；如果像指标清单、审计报告或把 A/B 分别填进同一套句式，必须重写。

以下两条是 GSB 理由的硬性证据约束，违反任意一条都不得提交：

- 理由中凡涉及执行过程、工具调用、命令、模型动作、完成或失败状态的描述，必须由对应 A/B 轨迹文件明确记录并能回指到具体事件。轨迹没有记录、与轨迹相悖或只能靠常识推断的内容一律删除；不得根据代码产物、录屏或个人判断补写轨迹，不能猜测、补全或虚构，证据不足时应标为 needs_evidence。
- 理由只使用冻结的轨迹、已提交的代码产物和 User Prompt。禁止写录屏、录像、截图、屏幕观察、本地或评价助手复跑结果、未提交到 Git 的脚本或测试、临时文件及其他场外环境信息；这类材料即使存在于审核目录，也不能成为 GSB 理由依据。

## 质检

批量导出前核对必填字段、枚举、两个不同 SessionID、单轮限制、Prompt 一致、A/B 独立容器、三个远端分支、三条快照 URL 的仓库和 SHA、两个产物的直接父提交、轨迹文件，以及与当前证据对应且理由非空的 GSB 评价。缺少录屏不拦截导出；没有当前 GSB 理由的题目直接跳过。工程故障或环境未重置时标记作废，不硬写有效 GSB 结论。

批量审核逐题读取冻结的 A/B 轨迹和代码产物并形成一条 GSB；证据哈希和审核模型均未变化时复用当前结果。单题审核能力始终保留，可对指定题独立生成或强制重新生成。批量汇总不得把跳过或失败的题伪装成已审核。
