# 证据归属与评分校准

本文件是AI制表的实施方法，基于26.09规范与试标表暴露的问题补充。用户负责项目、Prompt与CLI执行；AI负责本文件描述的后处理。

## 1. 每轮建立证据对应关系

保留以下最小信息，可存独立证据报告，不要求新增正式表列：

- 轮次：SessionID、TurnID/PromptID、实际顺序、起止事件、有效或排除原因。
- 需求：本轮目标、约束原文、验收场景；一次或多次纯“继续”等恢复指令都关联原始任务，不改写原始 Prompt，也不拆成可导出轮次。
- 产物：首轮前快照、该轮结束状态及重建依据；未跟踪文件和未提交改动也纳入，不只看 `git log`。
- 证据：轨迹文件及行/事件位置、对应状态的文件/函数、调用或测试输出。
- 归属：被测模型行为、用户介入、评价助手行为；证据强度区分直接记录、独立复现、静态推断、尚未验证。
- 结论：支持哪些维度、问题是否在本轮结束时仍存在、影响范围及对应评分锚点。

不因为一个父任务启动了子代理就多出用户轮次；可将子代理的已证实工作纳入原轮过程，不重复计工具调用。日志摘要不能替代缺失的原始Prompt或验证输出。若导出包含重试/重复事件，按稳定事件ID和链路确认后去重；所有纯恢复指令及其后的模型事件按实际顺序并入被恢复的原提示词，Excel 只保留原始 Prompt 对应的一行，不出现 Prompt 为“继续”“请继续”等恢复数据。同文本但属于实质性新提交的用户消息仍分别记录。

若用户在CLI执行后手动改了代码，优先还原原轮产物；无法归属的改动标明，不能算成模型成绩。多个真实SessionID不能为方便制表而改写合并，需用辅助关联信息表达同题背景。

## 2. 评分前先核验真实需求

优先覆盖用户明确要求与高影响边界，选择有关场景验证，不给每题套相同测试清单或测试数量。检查范围包括按题目需要的：正确性、漏需求、回归、错误处理、代码质量、额外复杂度、硬编码/假数据/占位实现、删改测试规避失败、无关破坏、安全及UI表现。

- 已有项目扩展通常归Feature迭代；修复已存在问题通常归Bug修复。不能因改动量大或新增模块就自动归0-1，也不能机械地把所有已有仓库任务都归Feature；看本轮主要意图和完整模块构建范围。
- 本轮类型与难度独立于整个会话题型。相同会话“功能迭代→修Bug”正常；同一仓库复用不等于题目雷同。
- 只有静态代码证据时写“代码实现/静态检查显示”，不写“已运行验证”。构建通过只说明对应构建结果，不能证明数据库迁移、并发、重启持久化、下载、UI交互等行为。
- 若应用提供 `review_commit`、冻结差异或提交文件清单，已提交代码应以这些材料为本轮变更依据；当前工作区 `git status` 或 `git diff` 为空不能反推本轮没有改动。
- 模型未加自动化测试并非所有题统一扣分。若Prompt明确要求测试，遗漏属于交付/约束证据；若无明示，则结合任务风险与实际验证充分性判断，说明具体未验证的行为。
- 不用新增验收要求强行扣分。隐性约束须能从业务目标、兼容性、仓库要求或必要正确性推出。额外改动需区分合理补边界与无关扩展，写出作用域或成本证据。

## 3. 过程与结果分开评分

### 先核对本轮实际停在哪里

按本轮PromptID和事件边界，确定是正常完成、仅探索/计划、等待结果，还是网络/服务/工具环境中断。调用了子代理不等于已收到结果；父会话只说“已启动探索并等待”时，不得把尚未返回的实现、后续轮次或当前最终仓库状态记为本轮交付。用户只要求方案时，方案本身可构成交付；用户要求实现时，只写计划不能算实现完成。

遇到429、RateLimitError、504、分类器超时、网络断开或供应商限流，先沿轨迹查找全部纯恢复指令，将恢复后的执行并入原提示词，再以最后一次恢复执行结束后的状态作为轮末。平台事件只记录在证据索引或 limitations，不能进入非满分描述、descriptionChecks 或 Bug/process 问题作为扣分依据。最终仍有未完成内容时，只根据原 Prompt 要求但轮末仍缺失的具体功能、文件、测试或交付物评价，并说明该部分本应由模型完成及其实际影响；不能用平台中断解释或支撑扣分。没有恢复机会且故障阻断了关键工作时，不把故障时尚未接线、未测试或缺少最终总结评为模型漏做，证据不足则记录排除或待补。

独立复跑出的问题是否属于该轮，仍须核对代码归属和模型当时是否获得完成机会。后补验证只证明对应状态的行为，不能替模型补造已做完的过程。


| 情况 | 校准方法 |
| --- | --- |
| 中途编译失败，本轮内修好并验证 | 轮末产物按实际完成度评；错误恢复与冗余影响执行/推理，不自动让交付也扣相同分 |
| 最后完成，但反复试错 | 交付与过程维度可以不同；不因结尾成功统一给5 |
| AI后补测试通过 | 能支持产物判断，不能证明被测模型做过该测试或规划完善 |
| 评价助手在独立副本因未装依赖构建失败 | 记录评价者、命令和环境原因到验证说明，不作为原模型执行扣分依据，也不在满分格里混写成原模型构建失败 |
| 规划低分只写“中途构建失败，随后修复” | 补齐实际阶段、工具调用及文件/命令仍不够；还须证明计划、依赖顺序或状态追踪的独立不足，不能借执行错误凑规划扣分 |
| 某文件多次读取 | 检查是否因文件更新、上下文缺失或新问题而必要；仅重复次数不证明无效 |
| 没有特定计划工具或开头没列清单 | 看真实拆解、阶段反馈与状态追踪，不能形式化固定扣1分 |
| 未拿到足够思考过程 | 用可见定位、决策与修复行为评价，注明依据范围，不断言隐秘思考或token数量 |
| 编译报错或某命令非零退出 | 查真实原因与影响；搜索无匹配、被终止进程、环境请求失败不自动等于模型缺陷 |

验证按任务风险选择。核对入口、数据变化、持久化和界面反馈时，只检查与本轮目标有关的环节；修复任务优先复现原触发条件，并检查能由该修复合理影响的相邻边界。没有固定测试数量、验收矩阵格式或工具使用次数要求。样表只提供字段与格式参考，它的分数、描述和问题归因不构成新案例的评分答案。

同一问题可影响多个维度，但必须分别建立关系：缺少分页影响交付；若Prompt明确要求分页也影响指令遵循；只有轨迹证据显示计划漏项或推理错误时才进一步影响规划或推理。不要五项统一连带扣分，也不要完全禁止合理的跨维度影响。

## 4. 分数与描述交叉检查

逐格执行 [五维依据完整性检查](description-quality.md)。先核对对应维度的负面判断、行为、客观后果是否齐全，再检查自然表达；“尚未验证”的具体范围与“已经发生”的产物问题须明确区分。

- 5分描述需有相应正向依据，不能只是“都完成了/没有问题”。交付5分同时存在已确认的轮末未满足需求、Bug或虚假成功时，必须回到评分锚点重判或澄清问题不属该轮目标；不能把缺陷藏进其他维度。
- 交付4分锚点要求主要需求完成且无虚假成功；核心缺陷或明显虚假成功不能仅称“小瑕疵”保留高分。按影响和原锚点判，不另创一律扣分公式。
- 低于5分要写出与所选档位对应的具体不足，不能只有正向过程罗列。分数不追求高低比例，也不模仿试标表分布。
- 指令遵循不能只写“没改无关文件”；还需逐项核对实际约束。没有用户原话或可信上下文，不把“未提交代码”等行为编成用户要求。
- 有问题时写触发、行为、证据、影响，兼顾过程和产物；无某类问题则据实写核验结果，不为结构捏造缺陷。
- 描述栏按第7节用自然语言写，保留事实与证据归属；不能靠删除问题、模糊判断或虚构个人体验让文字显得自然。

## 5. 批量检查的范围

每日题型偏序、总量、重复题只能在掌握的批次范围内统计。单个会话不能证明团队全天达标；没有历史题库不能保证全局不雷同。按同一用户提供的批次日期口径统计，区分轨迹产生时间、制表时间与实际提交时间。缺实际审核结果时不编造合格率。

每轮模型评分与记录本身的材料完整性/选题风险分开：有分数的维度只能填3—5，五项齐全时总分不得超过21。初评超限时在同一次审核中回查真实过程不足并校准对应分数和完整依据，不直接返回超限结果，不机械减分、虚构扣分、改Prompt、改SessionID或删轮美化数据。低分也不代表存在代码 Bug，仍须独立核对功能完成度和其他材料规则。

## 6. 从最新版样表学习

学习09-09试标表时，读取 [分维度写法与打回经验](sample-lessons-2026-09-09.md)。重点阅读审核通过记录的具体表达，并按用户说明将有审核备注的记录视为有过打回历史。状态、当前文字和历史意见分开核对，既不将所有通过行奉为标准，也不忽略历史问题。新样表出现时重新定位工作表与Excel行号，不沿用旧版行号解释新内容。

## 7. 自然语言描述要求

适用于Excel的五项评分依据和“其他问题”，是用户明确提出的文字要求。只调整评价描述的写法，原始Prompt、ID、代码、引文和其他事实字段保持原样。用户只要求改写时，沿用已核实的事实与评分；发现事实冲突再说明并单独处理，不能在润色中悄悄改分。

### 表内怎样写

- 直接说具体表现。能说“下载的图片里，第二行文字被标签挡住”，就不写“交付边界覆盖不足，影响产物可用性”。让读者不用翻译术语就能明白问题。
- 每格用一段连贯文字写清依据，不换行列提纲，也不硬凑字数、句数或统一开头。简单问题简短说明，复杂问题保留必要解释。
- 围绕本维度最有依据的表现展开。无需每格都先夸后批、重复需求清单，或以“因此给X分”“整体可用但仍有提升空间”收尾；分数已在相邻单元格。
- 用真实操作阶段及工具调用定位不足，描述正文必须保留相关文件名、路径、函数名、命令、参数、关键报错和数据；不能为让文字显得自然就删除、改名或模糊处理。技术引用直接作为普通文本放进句子，不添加反引号或装饰符号。完整日志和冗长输出放同轮证据索引，必要技术引用仍留在表内，按 description-quality 的操作节点与原文引用要求复核。
- 用具体动作替代抽象短语。例如“只检查了文字有没有超出画布，没有检查文字会不会相互遮挡”，比“验收闭环缺失、边界推导不足”更清楚。不把常用专业名词一概删掉，也不用生硬中文替换必要的代码名称。
- 不套用“核心目标满足—局部偏差—主体交付成立”等固定结构，不写“触发节点：”“实际行为：”“证据：”“业务影响：”等标签，也不使用“综上所述”“总体而言”“因此给X分”等评价套话。禁止 Markdown 标题、列表、强调符号、反引号、箭头、Emoji 和勾选图标；事实间的因果关系直接用中文说清楚。
- 不写“以下是”“作为 AI”“基于以上分析”等前言，不用机械总结收尾。逐项比较五格的开头、句式、事实和结论；两格内容重复、文字重复比例过高，或语义相近却只替换维度名和少量同义词时，必须分别重写。每句话都要主谓关系清楚、前后衔接自然，不能留下成分残缺、搭配生硬或未写完的连接语。
- 不虚构“我手动试了”“作为用户我觉得”“人工复核确认”等经历或身份。模型做的检查与后补验证仍要分清，可以自然写成“模型只做了语法检查；后续在浏览器复现时发现……”。AI评价来源保留在交付说明，无须每格重复宣告。

### 写法示例

以下只演示写法，不是默认评分结论；实际使用必须有本轮证据，不得照搬案例事实。

| 生硬或空泛的写法 | 自然且具体的写法 |
| --- | --- |
| 核心流程可运行，长文本场景存在布局边界缺陷，主体交付成立。 | 海报可以生成和下载。不过，原话排成三行时，第二行会被情境标签挡住，第三行又和页脚挤在一起，下载的图片也有这个问题。问题出在海报视图的正文布局，文字变多后没有给标签和页脚留出空间。 |
| 规划拆解合理，状态追踪完整，但验收覆盖不充分。 | 先定义事件，再做海报视图，最后接入记录列表，步骤安排清楚，也及时更新了完成状态。漏掉的是实际页面验收：没有检查多行文字的排版和下载结果，最后把视觉检查留给了用户。 |
| 执行路径基本高效，存在少量冗余往返及验证失配。 | 修改前先读了相关文件，修改和语法检查都成功了。检查换行时反复换了几组数据，但测试宽度和实际海报不一致，也没有检查文字是否互相遮挡，这几次检查没能发现排版问题。 |

### 五个维度分别回答什么

- 交付：本轮实际交出了什么，哪些用户操作可用，什么条件下仍会出问题。构建、真实业务测试和仅静态查看按实际范围写清。
- 指令：保留短而准确的被违背约束原文，再说实际行为哪里不符。满分须表明逐条核对，并列出与本题有关的主要约束，不能只说“没有越界”。
- 规划：说明拆解、阶段衔接和状态更新。不能用模块分层代替过程证据，也不以缺少TODO工具或独立验收文档作为唯一扣分理由。
- 推理：定位真实判断或验证步骤，引用相关命令、测试文件/用例或函数，写清模型可见的判断与操作、哪里不成立及证据支持的客观后果。测试问题须说明实际输入、返回行为与有需求依据的预期差异；不能只写“空文本返回结果不合理”。按 description-quality 的“推理扣分必须写出判断、行为与可核查结果”复核，正确发现并修复问题不自动扣分，仅列功能和测试通过也不能证明推理满分。
- 执行：说明具体工具动作是否有效，失败后怎样恢复，哪次重复没有必要。总调用数、文件数和耗时只能作背景；不据此独立扣分。

### 导出前通读

逐格检查：能否直接读懂做了什么、具体哪里有问题、为什么影响本项评分；定位是否足够；是否堆了并不帮助理解的数字和术语；五格是否机械重复同一结构或表达相近的同一结论；句子是否完整通顺；改写是否改变了问题严重程度、验证范围或执行者。发现问题就针对该格重写，不靠同义词替换、刻意添口头禅或制造错别字处理。不使用不可靠的AI检测器分数代替逐句检查，也不伪装人工来源。
