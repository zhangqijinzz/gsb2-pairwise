# 五维依据的完整性与自然表达

本页用于评分后、保存 JSON 或写入 Excel 前的逐格检查，补充已有五维锚点，不另设扣分档位。依据是用户反馈的返修问题：规划描述只有动作经过，未说明规划上的不足；执行描述使用主观感受词，且没有交代验证缺口的具体影响。

## 非满分依据必须说清什么

对每个3—4分维度，检查下列三项内容是否能从正文直接读出，并能回到本轮证据：

| 必需内容 | 判断方法 |
| --- | --- |
| 本维度的明确不足 | 读者能知道哪里不合适，例如“编辑顺序漏掉了读取现有文件这一步”。只写“未先读取，失败后补读”是经过，不足的归属仍不清楚。 |
| 具体行为与位置 | 指明本轮哪个操作、需求、函数或界面状态支持判断，不能只说“规划不够完善”“执行不够严谨”。 |
| 证据支持的后果 | 写出实际失败、返工、遗漏的交付，或明确限定的验证范围。例如编辑被拒绝后需要补读重试，或现有检查未覆盖某项交互状态。没有事实支持时，不补写耗时、用户损失、功能异常或泛化风险。 |

三项是内容检查项，不是单元格中的固定标题或固定句式。必要验证遗漏的严重程度须结合本轮目标、已覆盖范围和原锚点解释，不新增“没做浏览器验证就固定给 4 分”等规则。自然写成一段即可，不统一套“整体完成了，但是……因此扣分”。分数已在相邻列，无需复述。

证据足以评价但原扣分理由不成立时，回到锚点重判并记录改分依据；必要证据确实缺失时，标明具体缺项，不能为了保留旧分而补造负面判断。仅受托润色旧记录时先保留原分，单独指出分数冲突，不静默改分。

## 操作节点与原文引用（本次打回要求）

每项指出不合理表现的描述必须同时保留操作节点和具体技术引用，直接写在描述单元格中；不能只放在 evidence 或配套索引里。自然表达不得删掉这些引用。

- 操作节点：写清本轮具体步骤及实际工具调用，例如“在代码修改后的最终验证阶段，通过终端执行……”。轨迹有可靠轮次、步骤或调用编号时可引用；没有编号就用证据支持的先后节点定位，不编造“第几步”。只有证据显示构建通过，才写“构建通过后”；没有提交记录或提交要求，不能套用“提交前”。
- 技术引用：保留与不足直接相关的真实文件名、函数名、命令或工具调用及关键参数。按实际操作引用适用项，不虚构不存在的函数或脚本。仅写“未验收”“用了错误参数”或“node: bad option”不足以定位。
- 命令失败：描述中保留导致失败的完整命令（含关键参数及目标测试文件/脚本路径）、关键报错原文、发生阶段和实际后续处理。不能用省略号、孤立报错或仅恢复命令代替失败命令。命令中的凭据脱敏并说明，不能为追求完整而泄露密钥。
- “可避免”需要额外依据：确认当时运行环境、参数支持情况以及模型可获得的信息。仅见非零退出或后续换了命令，不能认定失败本可避免，更不能自动扣分。
- 验证遗漏：明确在哪个收尾/验证节点执行了什么检查、其实际结果，以及未覆盖原需求中的哪项行为。材料不全与已证实遗漏分开；不能仅凭没有浏览器记录认定功能损坏。
- 若无法取得失败命令或位置，先回读原始工具调用及结果；仍缺失时撤回无证据的指控，必要维度标待补证据。用户给出的示例命令不是该题真实证据，禁止照抄补全。

例如，仅在轨迹确实支持全部事实时，可以写：“在本轮最终验证阶段，模型通过终端执行了 npm run build，构建通过后直接结束回复。该检查未覆盖原需求中语速切换后的时长更新，无法据此确认该交互是否正常。”涉及组件文件或函数时补入实际名称。此例不能作为固定扣分理由。

保存前逐条核对每项负面判断的“操作节点、实际调用、技术引用、结果与后果”，并回到同轮原始证据核实。缺少定位或失败命令的旧描述不能仅靠润色补齐。

## 五个维度各自判断什么

| 维度 | 描述中要落到的判断 | 容易混淆的边界 |
| --- | --- | --- |
| 交付完整性 | 哪项本轮需求在轮末没有完成、结果在哪个操作下不符合要求，以及实际影响 | 未验证不等于功能已坏；已修好的中途错误不能继续写成轮末缺陷。 |
| 指令遵循 | 哪条真实约束被违反、实际做法是什么、偏离了什么要求 | 未要求的增强功能或特定测试形式不能冒充用户约束。 |
| 任务规划 | 哪个必要步骤、依赖顺序或状态跟踪安排有遗漏，以及它带来的返工或遗漏 | 没有 TODO 文档不等于没有规划；一次工具失败不能自动推导“完全没有前置检查机制”。只有证据表明推进顺序遗漏前置条件时才在规划维度归因。 |
| 推理能力 | 哪个可见判断或假设不成立、遗漏了哪个条件，以及它如何使方案或排查方向出错 | 不猜不可见的内部思考；工具参数错误本身不一定是推理错误。 |
| 执行能力 | 哪次操作、工具使用、错误处理或必要验证不到位，以及可观察的失败、补救动作或未覆盖的具体行为 | 不用“不算完全干净”“不够漂亮”“差点意思”等感受词代替事实，不把所有非零退出都当执行缺陷。 |

同一个事实涉及多个维度时，分别建立归因，不把“未先读取”复制到规划、推理和执行三格后统一扣分。

## 验证缺口怎样写

- 先核对本题实际验收目标和已有验证方式。没有浏览器交互记录，不自动扣分；命令行任务、已由其他方式充分覆盖的行为，不能硬加浏览器要求。
- 证据明确显示本轮只做了构建和算法检查、没有覆盖要求中的界面状态时，可以写“这些检查没有覆盖语速切换后的界面更新，现有验证无法确认显示时长是否随选择变化”。这里描述的是验证范围，不能改写为“切换语速后显示错误”。
- 只有材料没有提供验证记录时，写“所提供轨迹未见……记录”，不能断言模型从未执行过该检查。需要该证据才能判断的维度用 `null` 并列缺项，不凭缺失记录给能力低分。
- “可能有问题”“存在潜在运行时风险”仍然模糊。应说清哪个实际需求下的哪项行为没有被覆盖；无法定位就收回这条泛化结论。

## 对本次打回文字的改写示例

以下只示范表达。使用前须核对本轮轨迹与原始需求，不直接套用示例事实，也不根据例句确定分数。

**规划低分，且顺序遗漏确有证据时：**

“编辑 README 前漏掉了读取现有内容这一步，直接修改被工具拒绝，之后才补读并重试。这处步骤顺序安排不当，增加了补读和重试操作。”

如果证据只能证明一次工具操作失误，应优先按执行事实判断，不能靠加上“规划阶段”四字硬凑规划扣分。规划给 5 分时应写该维度的正向证据；若另述已恢复的执行错误，交代它为什么没有破坏规划安排，不留下未解释的分数冲突。

**执行低分，且需求与验证范围确有证据时：**

“README 首次修改因未读取文件被拒绝，补读后才完成修改。随后通过了构建和算法检查，但这些检查没有覆盖语速切换后的界面更新，现有验证无法确认显示时长是否随选择变化。”

如果后补检查证实交互正常，应保留原模型验证范围的事实，并分别归属后补结果；不能把后补结果写成模型已经验证。

## 规划定位与失败归属（再次打回复核）

保存每项描述前，先确认“谁在何时操作什么、发生什么结果、为什么影响本维度”，再核对分数。以下检查也适用于 integration review-only，必须在同一次审核中完成。

### 规划扣分不能只复述执行错误

- “中途”“随后”“过程中”“后面修好了”不能单独作为位置。必须补上有证据的阶段或步骤及具体对象：在哪个文件/函数修改完成后、哪次命令或工具调用前后，计划漏掉了什么依赖、检查步骤或状态更新。已有真实步骤编号可引用，没有编号不能补造。
- “中途构建失败属于编辑执行错误，随后定位并修复”既缺定位，也没有证明规划不足。不能仅加上“最终验证阶段”就保留规划扣分；应回读计划、推进顺序和状态记录，找到该维度独立的不足及后果。只有执行错误时，按执行维度评价，规划回到自身证据评分。
- “完成领域字段后执行构建时”只是定位方式示例；只有原轨迹支持，才能补上实际领域文件及完整构建命令。真实规划缺陷必须直接写在规划描述中，不借执行问题凑低分。

### 测试脚本调整须核对调整前的事实

“虽然中途测试脚本需要调整”不能作为规划扣分依据。它没有说明具体对象、模型行为、调整前结果，也不能证明规划本身有缺陷。涉及测试脚本调整的负面判断，先回读同轮工具调用、返回结果和文件变更，再检查：

- **发生节点与对象**：在哪次验证或哪项操作之后，通过什么工具执行了哪条完整命令；指出真实脚本路径及涉及的用例、函数、断言或配置项。只写“测试脚本”“最终验证阶段”仍不足；没有可靠行号或步骤编号时不补造。
- **调整前行为与结果**：模型当时设置了什么测试前提、断言或调用方式，运行后具体哪项断言失败、实际值与预期值是什么，或返回了什么关键报错。原命令须与该次输出配对；“需要调整”“测试没过”“后来通过”不能代替调整前的客观结果。没有执行记录的静态发现须明确标为静态检查，不编造失败输出。
- **实际调整与后果**：核对修改的是测试夹具、断言、启动配置还是业务实现，写清与扣分直接相关的改动以及实际重跑、返工或未覆盖的需求。仅有最终修正后的脚本不足以证明先前写错了什么。不能把修改测试预期后通过直接当成功能已修复，须对照原需求判断预期是否正确。
- **规划的独立不足**：只有原计划或推进记录能证明遗漏必要准备步骤、依赖顺序或状态更新，并与上述结果存在事实联系，才能归入规划扣分。补齐脚本名和报错仍不能代替这层归因。正常 TDD 的预期失败、合理调试、按新证据修订测试以及评价助手的环境准备，不自动构成规划不足。

保存前用正文回查“具体节点和脚本位置 → 当时做法 → 调整前结果 → 本维度不足与后果”；规划扣分须额外核实独立规划遗漏，执行问题不必牵连规划。这不是单元格的固定句式；用连贯中文保留能核验该扣分点的引用，不能让另一维度或 evidence 代为提供必要内容。缺项时先补查；证据足够但原扣分不成立则按锚点重评，关键材料确实缺失则列出缺项、必要维度留空，不保留模糊扣分、不自动改满分、不补造断言或报错。

### 命令原文必须与失败事件配对

- 将原始工具调用的命令、实际运行目录（影响定位时）、测试文件/脚本、对应返回结果逐一配对。描述保留完整失败命令和关键报错，恢复命令也按原文引用，不用孤立的“node: bad option”加“npx tsc”替代。
- Node 参数不支持的评价须引用实际参数及实际目标文件；示例 `node --experimental-strip-types test.ts` 不能补作真实命令。若调用的是包脚本，引用实际包脚本命令，并在可核实时补出脚本对应的文件。
- “可避免”还要有当时环境版本、支持情况或模型已读到的前置要求等依据。缺少这些信息，只陈述已核实的行为及后果，不追加主观定性；原调用缺失时列明证据不足，不虚构完整上下文。

### 推理扣分必须写出判断、行为与可核查结果

- “从测试输出中识别出空文本返回结果不合理”只说明发现现象，不能单独支撑推理低分。须回读该轮具体测试命令、测试文件/用例、函数实现及相应输出，定位是哪一次验证暴露的问题；描述正文保留实际阶段和相关命令、文件或函数引用。
- 写清模型在此之前可见的具体判断和做法，例如是否将空输入当作有效内容、是否误解了返回值约定、是否遗漏了已有分支条件；再说明哪条原始需求或真实上下文证明判断不成立。不能仅凭产物错误臆测模型内部思考。
- 客观后果写出真实输入条件、实际返回值/状态/行为，以及需求支持的预期结果和差异；有实际重复排查或返工时可说明具体操作。不能仅写“不合理”“边界考虑不足”，也不能把未运行的静态推断写成测试结果。没有空文本行为约定或必要正确性依据时，不自行新增验收要求。
- 如果扣分针对错误诊断，引用模型当时的实际归因、按该归因执行的检查/改动及对应结果，说明为什么无效；纠正后的处理仅按真实记录补充，不靠“后来修好了”替代错误判断的依据。
- 正确地从测试中发现问题并修复，本身可能是有效推理。只有证据证明此前存在理解、条件推导、根因判断或不必要试错的不足，才据此扣推理分；不能因测试暴露 Bug 就自动在推理维度扣分，也不自动改为满分。
- 保存前检查推理非满分格能否直接回答：哪一步、引用什么原文/文件/命令、模型做了什么判断与操作、哪里不成立、产生什么可核查后果。缺项时回查原始事件；材料足够但扣分不成立则按锚点重评，必要证据缺失则标明具体缺项。不能为保留旧分补造命令、返回值、预期行为或测试文件名。

### 满分描述与复验失败分开核对

- 先区分被测模型原会话、评价助手独立复验、用户操作和外部环境。评价侧首次运行因未安装依赖失败，不是被测模型的执行失误；不能仅因这个插曲把执行评分改为 4。
- 对评价助手或环境造成的失败，把执行者、独立副本、真实命令、缺失依赖及后续实际结果保存在 evidence/验证说明中，不在执行能力满分描述里孤立写“构建失败”。若正文需要说明验证范围，明确这是评价助手复验环境的问题，原模型在原会话中的操作是什么，两者分别有什么证据。
- 执行能力 5 分须由原模型准确且必要的工具操作及其结果支持，不能拿评价助手后补通过当作原模型已验证。仅把负面句删掉并不能证明满分；仍要回看完整轨迹。
- 若确认失败由被测模型自身的错误操作造成且构成执行不足，即使本轮修复成功，也须按执行锚点反映真实不足；轮末修复成功可支持交付判断，不能自动抹平过程问题。预期的失败用例、合理的诊断尝试和环境故障不自动扣分。
- 5 分格中若出现失败、错误、遗漏、返工等表述，逐条回查执行者、原因和维度归属；这是语义复核触发条件，不是按关键词自动降分。无法解释的评分矛盾不得保存为 ready；证据不足时保留明确缺项。

## 保存前逐格复读

按“执行者与事件配对 → 具体位置及原文引用 → 维度归因与分数 → 行为与后果 → 自然表达”的顺序检查五格。发现缺项时先回看证据，重写对应描述，再复核：

- 非满分格三项必需内容齐全；满分格写出具体正向行为和核验结果，不仅复述“高效”“合理”等锚点词，未夹带无法解释的负面结论；空分格说明具体证据缺口及影响。
- 五格没有共用一段泛泛评价，没有机械重复开头、刻意口语化、密集行号或与本题无关的术语。每格保持单段，不使用 Markdown、反引号、箭头、Emoji、勾选图标、固定要素标签或“综上所述”“因此给X分”等套话。文件名、路径、函数名、命令、参数、报错和关键数据属于事实，必须原样保留为普通文本；完整日志放索引。
- 五格两两比较，不能出现内容完全重复、文字重复比例过高，或语义相近却只替换维度名称和少量同义词的情况。每格只写本维度有证据的判断，句子须完整通顺；出现“以下是”“作为 AI”等前言、机械总结、成分残缺、搭配生硬或未写完的连接语时，整格重写后再检查。
- 文字像一份针对实际问题的简明说明。“整体不错”“仍有提升空间”不能替代扣分依据。改写后仍能追溯行为、影响和执行者，原分与原事实没有被润色改变。
