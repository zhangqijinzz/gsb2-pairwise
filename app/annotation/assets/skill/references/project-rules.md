## 选题类型与难度

| 类型 | 判定 |
| --- | --- |
| 0-1代码生成 | 基于需求构建新项目或完整模块 |
| Feature迭代 | 在已有功能基础上扩展 |
| Bug修复 | 逻辑修复、报错排查、安全漏洞修补 |
| 代码理解 | 解释逻辑、寻找风险、回答技术细节 |
| 代码重构 | 性能、可读性、解耦等优化 |
| 工程化 | 环境配置、依赖、CI/CD |
| 代码测试 | 单测、集成测试等 |

每天题型分布：0-1代码生成 / Feature迭代 / Bug修复 > 代码理解 ≈ 代码重构 > 其他。原文没有百分比配额，不自行编造。

| 难度 | 人类执行视角 |
| --- | --- |
| 简单 | 沿已有模式机械修改或局部实现，核心判断少；多文件同模式也可能简单 |
| 中等 | 理解局部至跨模块调用/数据流，有实现决策和边界，不需重设计架构 |
| 困难 | 整合多个模块/系统约束，关键取舍，复杂状态、兼容性、权限、并发、性能或异常链路 |
| 地狱 | 极高决策复杂度，深度项目理解、架构判断、多步复杂调试，大量正确性边界 |

首轮严禁简单；后续因模型产物质量产生的简单 bugfix 可以提交。原文判定同时满足至少两项为过于简单：单文件局部/纯函数实现；无仓库上下文依赖；大多数模型一轮完美交付且无需规划/排错；单一文件/语言、不涉及前后端或跨服务。不能仅因本次一轮完成就判简单，也不能人为拆文件抬难度。

## 环境、轮次与时限

- 首轮前一次初始快照，格式 `https://github.com/<org>/<repo>/commit/<40位完整SHA>`；同会话复用。不用短SHA、分支或tag。远端须评测团队可访问。
- 已提交快照不要 force-push/rebase 改写历史。凭据、.env、真实连接串/token不进仓库；发布前同时检查初始快照所含文件和 .gitignore 对 .env/密钥文件的覆盖，外部依赖只记类型和版本。检查规则缺失时如实记录，不为评价悄悄改变首轮前快照。
- 同会话 Harness、版本、系统、可复现等级、快照相同。语言/框架按本轮实际涉及填写。
- Harness决定system prompt、工具集和agent loop，版本升级也可能改变这些内容；同一模型跨Harness的表现不能直接互比，跨版本汇总须保留环境差异。
- 一个实质性用户提问与对应模型执行链计一轮，最多10轮。明显网络/工程故障不计；模型中断后一次或多次仅用于恢复执行的“继续”等短指令全部并入上一轮，不因恢复次数增加轮数。
- 所有有效轮次均保留在原始清单。正式评价的五维单项只能为3—5且总分不超过21；初评超限时由审核模型回查真实证据并在本次任务内校准后再保存。工程故障不具反馈价值的轮次按原规则排除。满10轮停止引导，开始新题；不换窗口继续旧题规避。
- 纯“继续”“请继续”等恢复指令不单独导出，Excel 不得出现以恢复指令作为 Prompt 的数据；审核范围从上一轮原始 Prompt 延伸到最后一次恢复后的模型执行与最终结果，仍只导出原始 Prompt 对应的一行。包含新增功能、约束或修复要求的后续消息仍按真实新轮次处理。
- 当天20:00前产生的数据当天交，之后可次日14:00前交。原文未注明时区，不自动套设备时区。
- 不允许返修，不合格直接拒收。高频不合格专家可能被拒收全部历史数据并停止参与。
- 原项目09/07—09/30总量不少于30,000，团队日产1,000—1,500（爬坡/模型不可服务等除外）。这是历史团队要求，不自动成为个人指标或新项目目标。

## 五维锚点（AI 应用）

锚点和分值不因表述返修而改变。每项非满分依据须按 [五维依据完整性检查](description-quality.md) 明确指出本维度不足、具体行为及证据支持的后果；不能为填齐三项而虚构问题，不能仅因没有浏览器验收或一次工具失败自动扣分。

五项各填3—5整数和必填依据，不用平均分替代；末轮成功不改变前轮表现，前轮失败也不限制末轮高分。

先完成五项初评，再计算总分。总分超过21时不得直接返回或保存，须重新检查真实轨迹中的过程问题，校准相应维度的分数和依据，直到总分不超过21。不得按固定顺序机械减分，不得虚构不足；控分结果仍与功能和 Bug 判断分开。

| 维度 | 5 | 4 | 3 |
| --- | --- | --- | --- |
| 交付完整性 | 一次完整跑通，明示及隐性边界完备，无虚假成功 | 主要需求完成可运行，极少细节遗漏，无虚假成功 | 核心可跑但有明确问题需调整，或存在轻微虚假成功 |
| 指令遵循 | 所有显式/隐式约束及细微格式均符合 | 核心及绝大多数次要约束符合，极小非关键偏差 | 核心目标满足但遗漏明确约束，需要调整 |
| 任务规划 | 清晰拆解，持续追踪，歧义求证 | 合理拆解总结，大部分状态及时，偶有不足（原文<25%） | 有方向但子任务粗、总结断续或状态遗漏明显 |
| 推理能力 | 理解深入、根因准确、思考投入匹配难度 | 方向正确高效，偶漏次要边界或少量冗余 | 理解主体但漏条件，多次试错，冗余或发散拖长等待 |
| 执行能力 | 工具准确必要，合理批量/并行，无无效探索 | 基本高效，少量冗余不影响整体 | 明显重复读取、检索或往返，最终完成但效率不足 |

百分比是原文锚点，不据此制造精确计量或机械扣分。计划不限定某个工具；调用数和任务规模不等于冗余；构建通过不证明业务全通过。

## AI 证据核验清单

- 交付：具体需求、文件/函数、报错、业务结果；虚假成功对照声称与实际改动。
- 指令：约束原文与实际行为；满分说明已逐条核对全部约束。
- 规划：拆解或状态追踪在哪一步出问题，不评价用了哪个工具。
- 推理：在哪里理解或归因错误，区分过度思考与思考不足。
- 执行：具体重复文件、失败命令、错误参数或恢复行为。
- 其他问题：五维未覆盖的问题，没有可空。

不满意原因兼顾过程和产物，具备“触发节点→实际行为→证据与影响”，不能只有“基本可用”“效果一般”。问题真实存在才写，不能为模板虚构缺陷。较好的原因可补根因和正确做法。环境/网络故障本身不作为模型能力问题。
