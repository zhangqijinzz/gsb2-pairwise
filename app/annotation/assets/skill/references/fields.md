# 提交字段与 AI 质量检查

保留用户模板的工作表、列序、数据和格式，修改时另存；不复制别人行作为用户数据。新批次模板和用户明确更新优先。当前来源以09-09的《【成都】CC_Codex 用户满意度收集（试标）-只读.xlsx》为准，不能把旧表中的空白批次、样例数或审核状态当作最新情况。

默认场景是用户已经在 Claude Code CLI 执行完成，AI接手生成实际 `.xlsx`。从真实轨迹自动提取 Prompt、SessionID、TurnID/PromptID和可确认的环境信息，并结合产物完成评分与理由。可从材料取得的字段不再要求用户手填；提交人、无法证实的初始快照等确实缺失项单独列出。没有新模板时沿用当前会话已有模板；制表不等于重新运行被测提示词。

应用集成的 `integration review-only` 模式只生成结构化评价记录，不在逐轮审核时制表。正式 Excel 在调用方冻结整个批次后一次导出：冻结清单包含全部登记题目、解析得到的有效及排除轮次、证据包哈希和选定评价版本。导出期间出现的新轮次或新评价进入下一版本，不能混入本次文件。

## 定位与检查边界

当前Word规定：Claude Code取本轮user消息的`promptId`；SessionID对应会话窗口，轨迹位于`~/.claude/projects/`。09-08旧版曾列Codex CLI的`task_started.turn_id`和`~/.codex/sessions/`，09-09已删除；这些只能用于技能扩展场景的真实取证，不能据此认定Codex数据属于当前项目范围。

AI读取角色、事件、Prompt、ID、时间、模型回复及工具结果，完成定位与过程/产物评价。子代理、工具调用或请求重试ID不能当用户轮次ID。实际结构不符时核对schema或列待补，不随机生成。

可机械检查：列与必填空值、分数3—5整数且总分不超过21、枚举、ID重复、同会话环境一致、快照完整SHA、附件存在。若有可靠会话顺序清单，再查漏轮、超10轮、首轮填简单。只有表格无法证明没有漏轮或某条确为首轮。

可靠清单至少包含 SessionID、每轮真实ID、顺序、有效或排除状态，以及排除原因和来源（例如轨迹中可核验的工程故障）。清单应来自实际会话记录、AI基于原始轨迹的核验结果或用户核验结果；不能仅从待查提交表反向生成再据此宣称无漏轮。缺少清单时报告“轮次完整性未验证”。

AI负责语义与证据检查：实质题型/难度、雷同、产物正确性、评分合理性、描述真实性与分数理由一致性。证据充分就完成评价，证据不足明确对应缺项，不自动转交人工。URL格式正确不证明远端可访问，Docker配置存在不证明环境可复现，须实际核查。

保留AI评价来源，不通过“AI口吻”检测或改写句式伪装人工来源，不为通过检查补造事实。

09-08旧来源第一批D2:D21为`==HYPERLINK(...)`异常公式（不是普通文本），缓存可能让读取值看似是正常URL；正式输出用有效commit URL，不能照抄双等号公式。提取URL不等于验证访问性。只读加载仅显示A1时检查worksheet dimension并重读，不误报空文件。

检查报告：输入/检查范围→已完成的格式与语义检查→逐轮评分和证据→具体行列缺项与未验证项→下一步。检查通过仅指本次范围，不替项目方验收。

## 环境值取证

Harness版本和操作系统取本次被测会话发生时的实际执行环境。当前电脑、评价助手环境、现在执行的 `claude --version` 可能与被测会话不同，不能直接回填。仓库在Linux服务器执行时不能因制表电脑是Mac就据此判断系统。项目依赖列表也不等于本轮技术栈：L列填本轮实际涉及项，多项用逗号分隔。

记录中的轨迹产生时间、证据采集时间、评价生成时间、文件导出时间和实际提交时间分别保存。Y列只填写已经发生并由调用方提供的实际提交时间，不能用评价或文件生成时间代替；尚未提交时留空。Z列可填“待审核”，但内部字段检查通过不能改成“审核通过”。skill、参考文件、评价模型和证据包版本保存在配套清单或证据索引，不占用原始 Prompt、审核状态或审核备注列。

批量导出只接收单项3—5且五维总分不超过21的完整评价。初评超过21时先由审核模型回查真实过程证据并校准评分和描述，不把超限结果直接交给导出。历史超限或低于3分的评价不写入正式表，需重新审核；排除轮次仍保存状态和有证据的原因。相同 SessionID + PromptID 视为复合重复并阻断正式导出，同文本但身份不同的真实输入分别保留。

同 SessionID 中出现不同版本或环境信息时先核对来源，保留事实冲突，不通过统一改成当前值掩盖变化；缺乏会话级证据时列待补。E列多个轮次可以指向同一完整轨迹文件；不同文件也可能属于同一会话，不能按文件数量计轮。

## 模板与导出回读

09-09来源第二批有15条数据（第2—16行），六组下拉仅到第15行；第一批有21条数据（第2—22行），六组下拉仅到第21行，两张表都漏最后一条。28列表头及六组枚举与旧版一致；不要把下拉保留的Codex CLI当作本批接收依据。新输出不能依赖这些设置自动保证合法：按现有枚举主动检查，必要时补齐目标提交区域的下拉与整数3—5校验。已有管理数据保持不变。

源模板与目标输出分清：更新用户已有正式表时保留原有行、工作表及格式；以别人试标表为模板新建用户提交表时复用结构，不把别人样例记录复制为用户交付数据。指定批次不明且会影响模型分组时查当前上下文，不能仅凭工作表排列或“第一/第二批”名称猜实际模型。

导出后回读检查：

1. 输出能打开，表头与列序正确；有效轮次清单中标记为 `included` 的轮次与实际输出逐条对应，不合规历史评价仍留在清单但不要求出现在正式表；复合键使用 SessionID + TurnID/PromptID，重复导入不悄悄新增重复行。
2. Prompt逐字符核对（允许已明确标记的附件补充说明），保留换行、空格、代码和原语言，不润色、不摘要、不静默截断。以等号等字符开头的Prompt或ID按文本写入，不误当公式；检查字符串是否因表格容量限制丢失。
3. ID/快照按文本保存，五项分数为数值整数3—5且总分不超过21，五项描述与对应维度对齐，无公式错误；缺证据的草稿列明缺项，不能拿空值冒充完整记录。
4. 校验覆盖全部数据行，不能只覆盖模板原行数；新建提交表可设置长文本换行、合适列宽和表头冻结，更新已有表时保留用户格式偏好。
5. E列和prompt附件中的名称/路径与实际交付文件一一对应；仅存在于评价电脑的绝对路径不等于接收方已取得文件。需要随表交付时保留原始轨迹，使用明确的附件相对路径或已提供的可访问链接，不把评价摘要伪装成原始jsonl。
6. 证据索引单独记录轮次、原始文件/事件位置、产物状态、验证方式和结果；AI评价来源放交付说明或独立报告，不能挤进原始Prompt或伪造外部审核意见。


## 新版样表暴露的导出问题

- 跨表也查 SessionID + PromptID 重复。09-09第二批第4行与第一批第22行是同一组ID，不能在新提交中重复计数。检查范围内发现重复时先确认是否历史留档，不能擅删用户已有数据。
- 非空检查之外逐格检查混入内容：审核意见、聊天指令、上一项目的skill说明、无关段落或孤立字符不能作为评分依据。第二批第15行R列为空，T列混入审核文字，说明修改后必须再次回读，不能只验证第一次生成的文件。
- 分数与文字交叉核对：第一批第11行U列为5，V列却说“扣1分”；发现这种情况须回到本轮证据统一分数和描述，不能机械地只改其中一个。本文不代替原表更改该评分。
- 使用 `scripts/check_submission.py 输出.xlsx --rounds-json 有效轮次清单.json` 做只读字段检查；清单从实际轨迹生成，格式见脚本 `--help`。检查工具可发现空值、分数类型/范围、枚举、ID重复、Prompt不一致和附件缺失；没有轮次清单时明确标为未检查，不能把字段通过当成轮次或语义通过。自然语言、验证归属、故障原因和评分合理性仍由AI结合证据复核。

## 轨迹路径填写规则（用户更新）

Excel E 列必须填 JSONL 文件的本机完整绝对路径，精确到文件名。不得填附件相对路径、目录、容器内部路径或网址。Docker 轨迹需先采集到本机；PinRu 导出使用导出包内该 JSONL 副本的绝对路径。独立使用 skill 制表时使用本机实际可访问的原始 JSONL 或已保存副本。多轮可共用同一文件。导出后回读 E 列，逐项确认绝对路径、`.jsonl` 扩展名及文件存在；材料缺失保留空值并报告，不编造路径。搬迁文件后需更新路径。附件清单仍可保留相对路径便于定位。
